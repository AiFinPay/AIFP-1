## Status Notice

This proposal is **withdrawn from the current AIFP-1 product/protocol scope**. mSECCO/on-chain token-credit or escrow-channel mechanics are not part of the current AIFP-1 merchant monetization profile.

Current AIFP-1 uses explicit resource metering plus payer settlement/receipt flows and current `100/0` economics. Internal points/billing systems or future streaming settlement mechanisms, if introduced, require a new/re-activated proposal with a current implementation and security model.

## Historical Motivation

The proposal explored reducing per-request on-chain overhead by using escrow/payment-channel semantics for high-frequency resource consumption.

## Why It Is Not Current Guidance

The current architecture should not require an AIFP-native on-chain credit/token or Passport-bound escrow simply to meter `$0.0005 / $0.002 / $0.005` actions. Metering can be off-chain while settlement is batched/aggregated through supported payment rails.

## Future Reconsideration

A future streaming-payment proposal would need to specify:

- whether it is an AIFP-1 extension or separate protocol;
- custody/escrow model;
- dispute and timeout behavior;
- exact settlement/fee semantics;
- identity requirements, if any;
- failure/recovery model;
- smart-contract security review;
- conformance vectors and reference implementation.

## Backward Compatibility

Historical references may remain as explicitly withdrawn/experimental design history. Current OpenAPI, schemas, SDK guides, and merchant integration docs must not require mSECCO channels.

## Security Considerations

Do not deploy or integrate an escrow/channel mechanism based solely on this withdrawn proposal. A future implementation requires a fresh security model and independent smart-contract review.
