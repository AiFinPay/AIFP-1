## Abstract

Proposes opt-in AIFP-1 merchant fee profiles from 100 through 500 basis points and three explicit merchant settlement modes. A signed payment quote must commit to an immutable fee revision, Treasury recipient, merchant settlement destination and route revision before the payer signs. `FIAT_AUTOMATIC` is the primary enterprise target: the merchant leg is sent directly to that merchant's approved financial-provider liquidation address for provider-managed conversion and bank payout. This proposal does not activate new economics, provider routes or contracts.

## Motivation

A quote that signs the merchant and gross amount while fee basis points, Treasury recipient or route economics can change later does not prove the payer authorized the final split. Sending merchant proceeds to a general wallet before a chosen automatic fiat route adds an unnecessary hop and is not the founder's target. Direct provider funding, however, needs explicit provider and legal approval, and must never silently change recipients if it is unavailable.

## Specification

### AIFP-1 fee profile

A merchant may opt in to an exact versioned fee profile with `treasury_bps` in the inclusive range 100–500. The amount is calculated with integer token base units using the profile's defined rounding rule. The Treasury and merchant legs MUST conserve the gross payer amount exactly. If the calculated Treasury fee is zero or either leg cannot be represented, the quote MUST be refused unless a separately approved profile defines a safe rule. No floating-point arithmetic is permitted.

This proposal does not change the current finalized baseline until accepted and implemented: AIFP-1 `100/0`, AIFP-2/x402 `0/0`. AIFP-2's route, fee model, quote and verifier are outside this proposal.

### Settlement modes

- `CRYPTO_DIRECT`: atomic split pays the merchant's non-custodial wallet and AiFinPay Treasury.
- `FIAT_AUTOMATIC`: atomic split pays AiFinPay Treasury and the merchant-specific provider liquidation address. The provider performs approved conversion and automatic bank payout. Merchant wallet-first is not required.
- `CRYPTO_WITH_OPTIONAL_OFFRAMP`: atomic split pays the merchant wallet; a later conversion requires merchant-authorized action and provider/legal approval.

The quote MUST bind mode, merchant and tenant, network/chain ID, asset/token and decimals, gross atomic amount, fee profile ID/revision/rate, Treasury address, merchant destination, settlement-profile ID/revision, nonce, expiry and payment authorization. The on-chain verifier MUST enforce all payment-relevant values in one atomic settlement. An HTTP preflight or database profile cannot prevent a post-signing contract-state race.

The settlement profile for the direct-fiat mode MUST be resolved before signing and include a customer-specific liquidation address, bank external-account reference, country, payout currency/rail, merchant-controlled return instructions and capability-evidence reference. Sensitive bank details and provider credentials MUST NOT appear in public quotes.

### Provider gates

A direct fiat route MUST remain unavailable unless the selected provider confirms for the platform account and route: merchant onboarding/KYB and beneficiary approval; direct smart-contract, third-party and AI-agent originated deposits; jurisdiction, asset/network and payout support; AML/Travel Rule data requirements; automatic conversion and bank payout; return handling and minimums. Provider acceptance is not bank-credit evidence. Unknown/negative capability blocks new quotes. No automatic wallet fallback is permitted.

Below-minimum micropayment aggregation is permitted only through an explicitly approved merchant-specific non-custodial or provider-managed capability with clear ownership, fee, refund and reconciliation behavior. AiFinPay MUST NOT pool merchant funds in its own wallet or claim unsupported minimums.

## Protocol / Route Scope

This is an AIFP-1 Standards Track economics and settlement proposal. It does not revise AIFP-2/x402, require AIFP-3 Agent Passport for external x402 compatibility, assign banking to AIFP-4, or require AIFP-5. AIFP-6 owns financial authorization, provider routing and financial evidence.

## Backward Compatibility

Classify as **MAJOR for the on-chain quote/contract format** and **MINOR for merchants who select a new versioned profile only after support is deployed**. Existing quotes retain their original signed recipients/economics and remain verifiable under their original contract version. Implementations MUST NOT reinterpret historic `fee_bps`, route IDs or merchant addresses using a newly edited profile.

No fields are added as silently required to existing AIFP-1/AIFP-2 wire formats. External x402 clients without Agent Passport remain supported through their existing compatible path.

## Migration Plan

1. Keep the current finalized 100/0 AIFP-1 and 0/0 AIFP-2 profiles unchanged until this proposal is reviewed and accepted.
2. Finalize a versioned quote schema and OpenAPI contract, exact integer test vectors, SDK/backend/MCP compatibility, merchant opt-in and revocation semantics.
3. Specify a new immutable contract or equivalent contract-enforced versioned route registry. Preserve deployed v1.4 unchanged. Obtain independent smart-contract security review and audit.
4. Implement profile storage as append-only revisions with tenant isolation and explicit activation. Resolve the route before issuing a signed quote.
5. Activate only individually provider-approved assets, jurisdictions, merchants, minimums, returns and payout rails. No production claims before testnet and provider sandbox evidence.
6. Roll back by disabling new quotes for a route and issuing a new profile revision. Never redirect an already-signed quote.

## Security Considerations

The Agent Passport identifies a managed agent but does not authorize spending. A separate, scoped payer authorization is required. The agent wallet remains non-custodial; AiFinPay MUST NOT collect its private key or any merchant key, and MUST NOT receive, pool or independently spend merchant funds. A profile change after signing cannot alter the signed route. Provider capabilities must come from authenticated API/webhook evidence and durable account mappings, not client-supplied flags. Enforce replay protection, idempotency, amount/velocity limits, kill switch, refund/return evidence and cross-tenant isolation.

Non-custodial design or use of a provider does not by itself establish that AiFinPay has no regulatory obligations. Obtain jurisdiction-specific legal advice before activation.

## Reference Implementation

A sandbox-only Bridge adapter and backend router/profile persistence candidates are in [aifinpay-web PR #434](https://github.com/AiFinPay/aifinpay-web/pull/434). They are not registered, runtime-tested or provider-approved. Their existence is not implementation or deployment conformance evidence.

## Test / Conformance Evidence

Before acceptance of implementation, cover exact split arithmetic and zero/dust, immutable recipient/fee/revision binding, mode changes, invalid KYB/jurisdiction, provider minimum/aggregation, no-fallback behavior, replay, partial settlement, provider failure/return, chain reorg, cross-tenant access and x402 compatibility. Node/PostgreSQL/contract suites and testnet/provider sandbox flows are required. No tests listed as written may be reported as passed without execution evidence.

## Deployment Considerations

No production route, contract, fee profile, provider agreement, financial operation, or public availability statement is enabled by this draft. A production rollout needs accepted AIP, independent contract/security review, provider written approval, legal/compliance review, tested rollback and separate explicit founder authorization.
