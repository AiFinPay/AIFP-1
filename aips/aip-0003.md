## Abstract

Defines a standardized HTTP transport for AIFP‑1 that adopts the IETF `WWW‑Authenticate` and `Authorization` header scheme for payment challenges and receipt credentials, while preserving the existing JSON‑body challenge as a backward‑compatible fallback. This AIP updates the protocol to interoperate with IETF‑style authentication mechanisms and to simplify client‑side handling of challenges.

## Motivation

* **IETF alignment** – MPP already uses the `WWW‑Authenticate: Payment …` header defined in `draft‑httpauth‑payment‑00`. Aligning AIFP‑1 with this scheme improves interoperability, tooling support, and standards‑track credibility.
* **Simpler client libraries** – Most HTTP client libraries already expose authentication‑challenge handling; using the standard header eliminates the need for custom parsing of JSON challenge bodies.
* **Future extensibility** – Header‑based negotiation allows easy addition of new authentication parameters without breaking existing agents.

## Specification

### 1. Challenge Delivery

* **Primary form** – The server MUST return an HTTP 402 response with a `WWW‑Authenticate: Payment` header. The header value is a comma‑separated list of parameters defined in Section 1.1.
* **Fallback** – For backward compatibility, the server MAY also include the existing JSON `payment_challenge` object in the response body. Clients that understand the header MUST prefer it; clients that do not understand the header MAY fall back to parsing the body.

#### 1.1 Header Parameters

| Parameter | Required | Description |
|---|---|---|
| `realm` | yes | Identifier of the payment realm (e.g., the merchant domain). |
| `resource` | yes | URI of the protected resource (same as the original request URI). |
| `amount` | yes | Amount to be paid, expressed in the smallest currency unit. |
| `currency` | yes | Currency code (e.g., `USDC`). |
| `nonce` | yes | Cryptographically‑random, single‑use nonce (≥128 bits). |
| `expires_in` | yes | Seconds after which the challenge expires. |
| `accept` | no | List of accepted payment methods (e.g., `stablecoin`, `card`). |
| `x‑payload` | no | Optional opaque data the merchant wishes to forward to the payment method. |

Example response header:

```text
WWW-Authenticate: Payment realm="example.com", resource="/api/data", amount="0.00001", currency="USDC", nonce="7f3c9a…", expires_in="600", accept="stablecoin,card"
```

### 2. Credential (Proof) Delivery

* **Client request** – The agent retries the original HTTP request, adding an `Authorization: Payment` header containing a base64‑url‑encoded JSON credential (see Section 2.1).
* **Credential format** – The credential is a JSON object with fields `nonce`, `amount`, `currency`, `method`, and a method‑specific `proof` value. The object is signed by the payment method (or AiFinPay gateway) and then base64‑url‑encoded.

#### 2.1 Credential Example

```json
{
  "nonce": "7f3c9a…",
  "amount": "0.00001",
  "currency": "USDC",
  "method": "stablecoin",
  "proof": "<method‑specific‑signature>"
}
```

The client includes it as:

```text
Authorization: Payment <base64url‑encoded‑credential>
```

### 3. Backward Compatibility

* Existing agents that only support the JSON‑body challenge will continue to function because the server MAY provide the body as before.
* New agents MUST check for the `WWW‑Authenticate` header first; if absent, they fallback to the body.
* This change is a **MINOR** version bump – it adds optional behavior without breaking existing implementations.

## Backward Compatibility

All existing AIFP‑1 deployments remain functional. Clients that implement this AIP gain access to the standard header‑based flow while older clients continue using the JSON body.

## Security Considerations

* The header values are subject to the same verification as the JSON body: the `nonce` must be single‑use, and the `expires_in` must be enforced.
* The credential signature must be verified against the appropriate public key (AiFinPay JWKS for gateway‑issued receipts or the payment‑method’s key for method‑native proofs).
* The use of standard HTTP authentication headers reduces the attack surface of custom parsing logic.

## Reference Implementation

* Updated middleware in the `sandbox/` demo now emits the `WWW‑Authenticate` header.
* Updated SDKs in `sdk/typescript/` and `sdk/python/` include helper functions `parseAifpChallengeHeader` and `buildAifpAuthorizationHeader`.
* Conformance tests are extended in `tests/transport/` to verify both header and body handling.

## Test Cases

The conformance suite must cover:

* Server response includes `WWW‑Authenticate` header with all required parameters.
* Client successfully parses the header and constructs the correct credential.
* Fallback to JSON body when the header is missing.
* Rejection of stale or reused nonces.
* Signature verification for both gateway‑issued and method‑native credentials.
