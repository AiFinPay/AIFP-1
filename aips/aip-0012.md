## Status Notice

This proposal is **superseded within the AIFP-1 repository**. Agent Passport is now treated as the separate **AIFP-3 identity protocol surface**, not as part of the normative AIFP-1 merchant payment object model.

The concrete reputation ranges, trust levels, endpoint names, and Passport-required feature list from this historical draft must not be treated as current AIFP-3 production guarantees unless they are ratified in the AIFP-3 specification and implemented/tested there.

## Historical Motivation

The proposal explored portable agent identity that could be consumed by merchant and payment systems for durable attribution, wallet/budget binding, and trust decisions.

## AIFP-1 Integration Boundary

AIFP-1 may consume authenticated agent identity where available, but AIFP-1 itself only requires that identity-sensitive features do not trust a caller-controlled identifier as if it were cryptographic identity.

Examples that may use AIFP-3 in the future:

- durable free-quota attribution;
- agent/wallet binding;
- delegated spend policies;
- merchant allowlists or trust policy;
- auditable agent ownership/identity.

Those features must follow the AIFP-3 specification rather than this superseded AIP.

## Backward Compatibility

Existing historical documents may reference `pp_*` Passport concepts for context. Current AIFP-1 API/OpenAPI/JSON Schema surfaces should not expose Passport issuance/retrieval as normative AIFP-1 endpoints.

## Security Considerations

Do not accept a Passport-like object merely because it contains an `agent_id`, public key, reputation, or signature field. Identity verification, key binding, delegation, revocation, and trust semantics belong to AIFP-3 and require their own security/conformance model.
