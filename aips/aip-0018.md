## Abstract

This document compares AIFP-1 (AiFinPay Payment Protocol v1.0.0) with MPP (Machine Payments Protocol) and derives a set of concrete convergence recommendations for AIFP-1's future development. Both protocols activate the HTTP `402 Payment Required` status code for machine-to-machine micropayments, but they diverge in transport design, payment-model extensibility, identity systems, and ecosystem maturity. This AIP is informational: it does not change wire protocol behavior, but it informs the standards-track work described in subsequent AIPs.

## Motivation

AIFP-1 was designed as a complete, opinionated payment system for AI agents, with strong identity, budget, and stateless verification guarantees. MPP (`draft-httpauth-payment-00`) was designed as an open, extensible HTTP authentication scheme for machine payments, with broad payment-method coverage and an ecosystem-driven governance model. Both are shipping systems with real integrations, so AIFP-1 cannot ignore MPP's design choices without losing interoperability. This comparison makes the differences explicit so that future AIFP work can adopt the best ideas from both worlds while preserving AIFP-1's enterprise guarantees.

## Comparison Dimensions

### 1. Executive Summary

| Dimension | AIFP-1 | MPP |
|---|---|---|
| **Core idea** | HTTP 402 + centralized gateway + signed receipts | HTTP 402 as standard auth scheme + pluggable payment methods |
| **Spec maturity** | Self-published draft (15-doc set) | IETF draft (`draft-httpauth-payment-00`), paymentauth.org |
| **Ecosystem** | AiFinPay-centric, single gateway | Multi-provider, co-developed by Tempo Labs + Stripe |
| **SDK breadth** | TS, Python, Go (planned 7) | TS, Python, Rust, Go, Ruby (5 shipped) |

### 2. HTTP 402 Transport Layer

#### 2.1 Challenge Delivery

| | AIFP-1 | MPP |
|---|---|---|
| **Primary form** | JSON body (`payment_challenge` object) | `WWW-Authenticate: Payment ...` header |
| **Header form** | Optional x402-compatible `WWW-Authenticate: AIFP ...` | Required, standard IETF auth scheme |
| **Encoding** | Plain JSON in response body | Base64url JCS JSON (`request`, `opaque` params) |
| **Negotiation** | `Accept-Payment: aifp/1.0` | Standard `WWW-Authenticate` / `Authorization` flow |

MPP follows the IETF HTTP Authentication framework (RFC 9110): the `Payment` scheme sits alongside `Bearer`, `Basic`, and `Digest`. This makes MPP challenges interoperable with any HTTP client that understands auth schemes. AIFP-1's body-form JSON is more human-readable and easier for agents to parse, but it relies on application-layer conventions rather than HTTP semantics.

#### 2.2 Credential (Proof) Delivery

| | AIFP-1 | MPP |
|---|---|---|
| **Mechanism** | `Payment-Receipt: <JWT>` header on retried request | `Authorization: Payment <base64url-JSON>` header |
| **Proof type** | Receipt Token (Ed25519-signed JWT) issued **after** payment | Credential (payment proof) submitted **with** retried request |
| **Flow** | Two-step: pay gateway → get receipt → retry with receipt | One-step: submit credential (proof) directly on retry |

AIFP-1 separates payment from access: the agent pays the AiFinPay gateway, receives a signed receipt, and retries the merchant with that receipt. MPP bundles payment proof into the credential sent with the retried request. MPP's approach is more direct; AIFP-1's approach gives the merchant a portable, reusable credential (within TTL) and enables stateless verification without understanding any payment network.

#### 2.3 Error Signaling

| | AIFP-1 | MPP |
|---|---|---|
| **Payment required** | `402` + challenge body | `402` + `WWW-Authenticate: Payment ...` |
| **Invalid proof** | `402` / `409` / `422` (custom error codes) | `402` + Problem Details (`RFC 9457`) |
| **Policy deny** | `403` (blocklisted) | `403` (payment valid, access denied) |
| **Rate limit** | `429` + `RateLimit-*` headers | `429` + `Retry-After` |

MPP uses RFC 9457 Problem Details for error bodies (`"type": "https://paymentauth.org/problems/verification-failed"`), which is more standards-aligned. AIFP-1 uses custom error codes (`AIFP-422-SIGNATURE`, `AIFP-403-BUDGET-EXCEEDED`) that are more specific but less portable.

### 3. Payment Model

#### 3.1 Payment Methods

| | AIFP-1 | MPP |
|---|---|---|
| **Supported rails** | Stablecoins (USDC/USDT/PYUSD) across 12 chains + fiat hybrid | Tempo, EVM/x402, Stripe (cards), Lightning (BTC), Solana, Stellar, Monad, NEAR Intents, RedotPay, custom |
| **Extensibility** | Fixed set defined by protocol | Anyone can define new payment methods with `request`/`payload` schemas |
| **Multi-method** | Challenge lists `accepted_assets` / `accepted_chains` | Multiple `WWW-Authenticate: Payment` headers, each a different method |

MPP's payment method framework is significantly more extensible. Any party can register a new method identifier and define its request/payload schemas. AIFP-1's model is fixed to the AiFinPay gateway's supported rails.

#### 3.2 Payment Intents

| | AIFP-1 | MPP |
|---|---|---|
| **Supported intents** | One-time payment (implicit) | `charge` (one-time), `session` (pay-as-you-go), `subscription` (recurring) |
| **Session/channel** | Not defined (future work) | Native session intent with payment channels |
| **Subscription** | Not defined (future work) | Native subscription intent with recurring access |

MPP natively supports three payment intents. AIFP-1 only supports one-time payments in v1.0.0. This is a significant gap for MPP's session (streaming) and subscription use cases.

#### 3.3 Pricing Model

| | AIFP-1 | MPP |
|---|---|---|
| **Pricing** | Fixed tiers: `standard` ($0.00001), `complex` ($0.00006), `premium` ($0.00010) | Merchant-defined, no protocol-fixed tiers |
| **Free quota** | Default 100 requests per agent | Not defined by protocol |
| **Protocol fee** | 1% flat | Not defined by protocol |

AIFP-1 bakes pricing into the spec; MPP leaves it to implementations. AIFP-1's fixed tiers simplify agent budgeting but reduce merchant flexibility.

### 4. Cryptography & Security

#### 4.1 Receipt/Credential Format

| | AIFP-1 | MPP |
|---|---|---|
| **Format** | JWS-signed JWT (EdDSA/Ed25519) | Base64url JSON with method-specific `payload` |
| **Claims** | `iss, sub, aud, resource, amount, nonce, iat, exp, kid` | Echoes `challenge` + `payload` + `source` |
| **Signature** | Centralized: AiFinPay issuer signs all receipts | Decentralized: each payment method signs its own proof |
| **Future format** | CBOR-COSE (CWT) for constrained clients | Not specified |

AIFP-1 receipts are issued by a single authority (AiFinPay) and verified by any merchant that trusts its JWKS. MPP credentials are payment-method-native: the proof is signed by the payment method's own key (e.g., EVM wallet signature, Tempo transaction signature). AIFP-1's model gives merchants a uniform verification path regardless of payment rail; MPP's model requires merchants to understand each payment method's verification procedure.

#### 4.2 Replay Protection

| | AIFP-1 | MPP |
|---|---|---|
| **Mechanism** | Single-use nonce (≥128 bits), linearizable nonce store | Single-use credentials (method-native semantics) |
| **Nonce store** | Merchant-maintained, TTL = 600s, requires linearizability | Payment method handles (e.g., on-chain transaction uniqueness) |
| **Multi-use** | Optional `quota` claim for multi-use within TTL | Not specified (credentials are single-use) |

#### 4.3 Key Management

| | AIFP-1 | MPP |
|---|---|---|
| **Root of trust** | AiFinPay issuer key (HSM/KMS), published as JWKS | Per-method keys (wallet keys, Tempo keys, etc.) |
| **Rotation** | `kid` rotation with overlap window, CDN-cached JWKS | Not specified by core protocol |
| **MPC** | Threshold Ed25519/ECDSA for enterprise wallets | Not specified by core protocol |

#### 4.4 Identity System

| | AIFP-1 | MPP |
|---|---|---|
| **Agent identity** | Agent Passport (Ed25519-signed, `pp_*`), `agt_*` IDs | `source` field (DID, address, account ID) |
| **Reputation** | Reputation score [0-1000], risk [0-100], trust levels | Not defined |
| **Delegation** | Delegation chains (≤5 levels) | Not defined |
| **Budgets** | Per-window, per-merchant, daily/monthly caps (atomic enforcement) | Not defined |

AIFP-1 has a significantly richer identity and governance layer. The Agent Passport, reputation network, delegation chains, and budget policies are absent from MPP. This makes AIFP-1 more suited for regulated or enterprise environments where identity and spend control matter.

### 5. Architecture

#### 5.1 Component Model

| | AIFP-1 | MPP |
|---|---|---|
| **Control plane** | Centralized AiFinPay backend (quoting, payment, receipts, ledger) | No centralized control plane; payment methods handle their own logic |
| **Data plane** | Merchant middleware (local Ed25519 verification) | Server-side SDK verifies method-specific credentials |
| **Gateway** | `api.aifinpay.io/v1/{quote,pay}` | No gateway; direct payment method interaction |
| **Settlement risk** | AiFinPay assumes risk for issued receipts | Merchant/payment method assumes risk |

AIFP-1 is a hub-and-spoke architecture with AiFinPay as the central hub. MPP is decentralized: each payment method operates independently. AIFP-1's model gives merchants a simple, uniform integration but creates a single point of dependency. MPP's model is more resilient but requires merchants to integrate with each payment method.

#### 5.2 Stateless Verification

| | AIFP-1 | MPP |
|---|---|---|
| **Mechanism** | Ed25519 signature verification against cached JWKS | Method-specific verification (on-chain, Tempo, Stripe API call, etc.) |
| **Backend dependency** | None for verification (JWKS is cached) | Depends on method (some require backend calls) |
| **Performance** | ~50,000 verifications/sec/core | Varies by method |

AIFP-1's stateless verification is its strongest architectural feature. Merchants can verify receipts locally at scale with no backend dependency. MPP's verification depends on the payment method; some methods (like Stripe) may require backend API calls, which reintroduces latency.

### 6. Transports & Integrations

#### 6.1 Transport Bindings

| | AIFP-1 | MPP |
|---|---|---|
| **HTTP** | Native (JSON body + custom headers) | Native (WWW-Authenticate / Authorization headers) |
| **MCP / JSON-RPC** | ACP (Agent Communication Protocol, Doc 16) | Native MCP transport defined |
| **WebSocket** | Not defined | Native WebSocket transport for streaming payments |
| **Browser** | Not defined | HTML payment UIs, payment links |

#### 6.2 SDK & Middleware Support

| | AIFP-1 | MPP |
|---|---|---|
| **SDKs** | TypeScript, Python, Go (planned: 7 languages) | TypeScript, Python, Rust, Go, Ruby (5 shipped) |
| **Framework middleware** | Not specified | Elysia, Express, Hono, Next.js |
| **Proxy** | Not defined | Paid API proxy server SDK |
| **CLI** | Not defined | `mppx` CLI for terminal payments |
| **Partner integrations** | Not yet | Cloudflare Agents, OpenClaw, Vercel AI SDK, MCP SDK |

MPP has a significantly more mature ecosystem with framework-specific middleware, a CLI tool, proxy support, and partner integrations. AIFP-1's SDK and integration story is still in development.

### 7. Protocol Features Feature-by-Feature

| Feature | AIFP-1 | MPP | Winner |
|---|---|---|---|
| HTTP 402 activation | Yes (body + optional header) | Yes (standard auth scheme) | MPP |
| Stateless verification | Yes (Ed25519 + JWKS) | Partial (method-dependent) | AIFP-1 |
| Payment method extensibility | No (fixed set) | Yes (anyone can define) | MPP |
| Payment intents | One-time only | charge, session, subscription | MPP |
| Agent identity system | Passport, reputation, delegation | Source field only | AIFP-1 |
| Budget controls | Native (atomic enforcement) | Not defined | AIFP-1 |
| Multi-chain support | 12 networks | Tempo, EVM, Solana, Stellar, Monad, Lightning | MPP |
| Fiat support | Yes (hybrid) | Stripe (cards) | Tie |
| Free quota | Default 100 requests | Not defined | AIFP-1 |
| Webhooks | Signed (HMAC-SHA256) | Not defined as core feature | AIFP-1 |
| Subscription support | Not defined | Native subscription intent | MPP |
| Session/streaming | Not defined | Native session intent + WS transport | MPP |
| Onboarding flow | Rich onboarding 402 | Not defined | AIFP-1 |
| x402 compatibility | Yes (migration path) | Yes (via EVM method) | Tie |
| MCP transport | ACP (Doc 16) | Native MCP transport | MPP |
| Framework middleware | Not specified | Express, Hono, Elysia, Next.js | MPP |
| Proxy support | Not defined | Yes | MPP |
| Payment links | Not defined | Yes | MPP |
| Refunds | Not defined | Yes | MPP |
| Discovery | Not defined | OpenAPI discovery document | MPP |
| IETF standardization | Self-published | IETF draft (`draft-httpauth-payment-00`) | MPP |

## Findings

### AIFP-1 Strengths

1. **Stateless local verification** — merchants never depend on a backend for per-request verification.
2. **Rich identity system** — Agent Passport, reputation, delegation, budgets.
3. **Simplified merchant integration** — one gateway, uniform receipt format.
4. **Enterprise-ready** — MPC wallets, KYC gates, SOC 2 / OWASP mapping.
5. **Onboarding flow** — rich onboarding 402 for agents that do not yet support AIFP.
6. **x402 migration path** — explicit migration endpoint for legacy x402 users.
7. **Settlement risk assumption** — AiFinPay assumes risk for issued receipts.

### AIFP-1 Weaknesses

1. **Centralized dependency** — single gateway, single issuer authority.
2. **Limited payment methods** — fixed to AiFinPay-supported rails.
3. **No session/subscription** — only one-time payments in v1.0.0.
4. **Non-standard transport** — JSON body challenge versus IETF auth scheme.
5. **Immature ecosystem** — no framework middleware, CLI, proxy, or partner integrations.
6. **Self-published spec** — not an IETF or other standards-track document.

### MPP Strengths

1. **IETF standardization** — `draft-httpauth-payment-00`, paymentauth.org.
2. **Extensible payment methods** — anyone can define new methods.
3. **Multiple intents** — charge, session, subscription.
4. **Rich ecosystem** — 5 SDKs, framework middleware, CLI, proxy, partners.
5. **Standard HTTP auth** — uses `WWW-Authenticate` / `Authorization` headers.
6. **Multiple transports** — HTTP, MCP, WebSocket.
7. **Decentralized** — no single point of failure.

### MPP Weaknesses

1. **No unified identity** — no agent passport, reputation, or delegation.
2. **No budget controls** — no native spend management.
3. **No free quota** — no protocol-level free tier.
4. **Method-dependent verification** — some methods require backend calls.
5. **No onboarding flow** — no equivalent to AIFP-1's rich onboarding 402.
6. **No webhook lifecycle** — no built-in payment event notifications.

## Recommendations

### For Merchants

- **Choose AIFP-1 if:** You want the simplest possible integration (one gateway, one verification path), need stateless verification at scale, require identity/budget controls, or operate in a regulated environment.
- **Choose MPP if:** You need multiple payment methods (especially cards via Stripe), want session/subscription support, prefer a decentralized architecture, or need framework-specific middleware.

### For Agents

- **Choose AIFP-1 if:** You need budget controls, reputation management, or operate in an enterprise context where identity and spend caps are required.
- **Choose MPP if:** You want the broadest payment method coverage, need session-based streaming payments, or prefer a decentralized ecosystem.

### For Protocol Development

AIFP-1 should prioritize:

1. **Standardizing the HTTP transport** — adopt `WWW-Authenticate` / `Authorization` headers per IETF auth scheme conventions. This work is expected to be addressed in a future standards-track AIP.
2. **Adding payment intents** — session and subscription support. This work is expected to extend AIP work on streaming payments and payment channels.
3. **Expanding the SDK ecosystem** — framework middleware, CLI, proxy support.
4. **Opening the payment method framework** — allow third-party payment methods to register while preserving AIFP-1's stateless verification guarantees.
5. **Pursuing IETF standardization** — submit AIFP-1 transport and receipt work as an Internet-Draft where it complements `draft-httpauth-payment-00`.

MPP should prioritize:

1. **Building identity/reputation** — agent passport, spend controls.
2. **Adding webhook/event system** — payment lifecycle notifications.
3. **Defining onboarding flows** — help agents that do not yet support MPP.
4. **Standardizing verification semantics** — ensure all methods support local verification where possible.

## Convergence Roadmap

The protocols are complementary rather than directly competitive. An ideal future state combines AIFP-1's identity/budget/verification model with MPP's extensible payment methods, multiple intents, and standard HTTP auth transport. There is a realistic path toward convergence, especially given both protocols' x402 compatibility layer.

Expected follow-on AIPs (not yet opened):

- **Transport convergence** — AIFP-1 `WWW-Authenticate` / `Authorization` header transport aligned with IETF paymentauth conventions, while retaining the JSON-body challenge as an opt-in fallback.
- **Payment method registry** — AIFP-1 extension that allows third-party payment methods to register `request` / `payload` schemas without giving up the hub-and-spoke security model.
- **Session and subscription intents** — AIFP-1 intents for pay-as-you-go and recurring access, building on existing payment-channel work.
