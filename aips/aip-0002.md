## Abstract

Ratifies AIFP-1 as the normative merchant-monetization protocol profile: HTTP `402` challenge, quote/settlement/receipt loop, Ed25519 stateless receipts, agent action pricing tiers, exactly 1% AiFinPay protocol fee (`100` bps) **deducted from the gross payer price**, creator/referral fee `0` bps, merchant settlement of 99% before external network/settlement costs, idempotency, and error handling. AIFP-2/x402 is a separate agent-payment route profile with `0/0` AiFinPay fees.

## Motivation

Establish the baseline payment protocol for monetizing AI-agent access to merchant resources with one unambiguous economic interpretation across protocol, SDK, backend, contracts, and settlement verification.

## Specification

### Payment Flow

1. Agent requests a protected resource.
2. Merchant returns `402 Payment Required` with an AIFP-1 challenge.
3. Agent requests a binding quote via `POST /v1/quote`.
4. The quote identifies the gross payer amount and its 99% merchant / 1% AiFinPay / 0% creator split.
5. Agent signs and broadcasts exactly the gross settlement amount from its own wallet according to the quoted route.
6. Agent submits the settlement reference through `POST /v1/pay` for verification.
7. After successful settlement verification, the agent receives an Ed25519-signed receipt.
8. Agent retries the request with the receipt.
9. Merchant verifies the receipt locally and grants access when all required checks pass.

### Pricing Tiers

The preset price is the **gross amount paid by the agent**, excluding external network/gas costs.

| Tier | Gross Price | Merchant 99% | AiFinPay 1% |
|---|---:|---:|---:|
| `standard` | $0.0005 | $0.000495 | $0.000005 |
| `complex` | $0.002 | $0.00198 | $0.00002 |
| `premium` | $0.005 | $0.00495 | $0.00005 |

### Fee Structure

Current AIFP-1 merchant-monetization profile:

- Gross payer amount: 100% of the quoted AIFP-1 action price.
- AiFinPay protocol fee: exactly 1% of gross (`100` bps).
- Creator/referral fee: 0% (`0` bps).
- Merchant settlement: 99% of gross before applicable network/settlement costs.
- Payer settlement amount: exactly gross; the 1% protocol fee is not added on top.

Canonical conservation rule:

```text
merchant_amount + protocol_fee_amount + creator_amount = gross_amount
payer_total_amount = gross_amount
```

A fee-on-top implementation that treats the AIFP-1 displayed/quoted price as the merchant amount and then adds 1% is not conformant with this AIP.

AIFP-2/x402 is economically separate and uses `treasuryBps=0`, `creatorBps=0` for AiFinPay's protocol fee profile.

### Receipt Properties

- Signature: Ed25519.
- Default TTL: defined by the active protocol/deployment profile; implementations must not silently extend expired receipts.
- Claims include audience, resource/scope, gross paid amount or quota, nonce/idempotency binding, and expiry as applicable.

### Idempotency

- Payment processing MUST be idempotent.
- `Idempotency-Key` and/or a unique settlement/payment identifier MUST prevent duplicate processing.

### Supported Networks

Network support is deployment-profile specific. Documentation MUST distinguish a chain being deployed from a chain being payment-live for a particular AIFP-1 route, asset, verifier, and economic profile.

## Backward Compatibility

Older examples and deployments using microcent tier values, a non-zero creator/referral leg, or fee-on-top AIFP-1 semantics are legacy/superseded economics. They may remain as historical evidence but MUST NOT be presented as the current AIFP-1 profile.

## Security Considerations

- Receipt forgery prevention via Ed25519.
- Replay protection via nonce/idempotency/settlement identity as appropriate.
- Settlement MUST be verified before a receipt is issued.
- Merchant-side receipt verification is fail-closed.
- Quote and verifier MUST agree that payer total equals gross and that the 99/1/0 split conserves the gross amount.
- A route MUST NOT be advertised as payment-live unless its quote, settlement verifier, receipt flow, and economic profile are mutually consistent.
