## Abstract

Ratifies AIFP-1 as the normative merchant-monetization protocol profile: HTTP `402` challenge, quote/settlement/receipt loop, Ed25519 stateless receipts, agent action pricing tiers, exactly 1% AiFinPay protocol fee (`100` bps), creator/referral fee `0` bps, merchant settlement of 99% before external network/settlement costs, idempotency, and error handling. AIFP-2/x402 is a separate agent-payment route profile with `0/0` AiFinPay fees.

## Motivation

Establish the baseline payment protocol for monetizing AI-agent access to merchant resources.

## Specification

### Payment Flow

1. Agent requests a protected resource.
2. Merchant returns `402 Payment Required` with an AIFP-1 challenge.
3. Agent requests a binding quote via `POST /v1/quote`.
4. Agent signs and broadcasts the selected settlement from its own wallet according to the quoted route.
5. Agent submits the settlement reference through `POST /v1/pay` for verification.
6. After successful settlement verification, the agent receives an Ed25519-signed receipt.
7. Agent retries the request with the receipt.
8. Merchant verifies the receipt locally and grants access when all required checks pass.

### Pricing Tiers

| Tier | Minimum Price |
|---|---|
| `standard` | $0.0005 |
| `complex` | $0.002 |
| `premium` | $0.005 |

### Fee Structure

Current AIFP-1 merchant-monetization profile:

- AiFinPay protocol fee: exactly 1% (`100` bps).
- Creator/referral fee: 0% (`0` bps).
- Merchant settlement: 99% before applicable network/settlement costs.

AIFP-2/x402 is economically separate and uses `treasuryBps=0`, `creatorBps=0` for AiFinPay's protocol fee profile.

### Receipt Properties

- Signature: Ed25519.
- Default TTL: defined by the active protocol/deployment profile; implementations must not silently extend expired receipts.
- Claims include audience, resource/scope, paid amount or quota, nonce/idempotency binding, and expiry as applicable.

### Idempotency

- Payment processing MUST be idempotent.
- `Idempotency-Key` and/or a unique settlement/payment identifier MUST prevent duplicate processing.

### Supported Networks

Network support is deployment-profile specific. Documentation MUST distinguish a chain being deployed from a chain being payment-live for a particular AIFP-1 route, asset, verifier, and economic profile.

## Backward Compatibility

Older examples and deployments using microcent tier values or a non-zero creator/referral leg are legacy/superseded economics. They may remain as historical evidence but MUST NOT be presented as the current AIFP-1 profile.

## Security Considerations

- Receipt forgery prevention via Ed25519.
- Replay protection via nonce/idempotency/settlement identity as appropriate.
- Settlement MUST be verified before a receipt is issued.
- Merchant-side receipt verification is fail-closed.
- A route MUST NOT be advertised as payment-live unless its quote, settlement verifier, receipt flow, and economic profile are mutually consistent.
