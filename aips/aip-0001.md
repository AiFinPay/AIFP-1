## Abstract

Defines the repository process by which AIFP improvement proposals are drafted, reviewed, accepted, rejected, withdrawn, superseded, and connected to implementation/conformance evidence.

## Motivation

Make protocol evolution transparent, reviewable, security-aware, and resistant to undocumented drift between normative docs, machine-readable contracts, implementations, and deployments.

## AIP Types

| Type | Scope |
|---|---|
| **Standards Track** | Protocol behavior, interfaces, economics, security rules, or network/profile representation |
| **Meta** | Governance/process changes |
| **Informational** | Non-binding guidance or design notes |

## Lifecycle

```text
Idea → Draft → Review → Last Call → Accepted → Final
         └──────────────→ Rejected / Withdrawn / Stagnant
Final ──────────────────→ Superseded
```

`Accepted` approves direction. For a payment-affecting Standards Track proposal, `Final` should also require implementation/conformance evidence appropriate to the risk rather than documentation merge alone.

## Roles

- **Author(s):** propose and maintain the AIP.
- **Repository maintainers/owners:** perform the actual repository review/status/merge decisions under the current GitHub ownership model.
- **Domain/security reviewers:** participate when the proposal affects their risk area.
- **Community/contributors:** may review and comment through the repository process.

This AIP does not invent a standing `AIP Editors` institution, voting `Review Board`, Security Council, or certification body unless such roles are formally designated elsewhere and linked from the repository.

## Decision Principle

A proposal should not advance with an unresolved blocking security/correctness objection. High-risk payment and smart-contract changes require the review/approval level defined by the engineering release policy; the author or generating AI agent should not be the only production approver.

## Compatibility

Classify changes by actual behavior:

- **PATCH:** editorial clarification with no machine/wire behavior change.
- **MINOR:** backward-compatible optional capability.
- **MAJOR:** breaking behavior/API/economic/security change requiring an explicit migration plan.

No fixed `12 months` parallel-support promise is created by this governance document. A major-change migration period must be proposed and justified for the specific change.

## Payment-Affecting Changes

An AIP that changes AIFP-1 economics or settlement behavior should identify and synchronize the affected:

- RFC/economics;
- OpenAPI/schemas/examples;
- SDK/backend route policy;
- contract/deployment profile;
- verifier/reconciliation logic;
- tests/security review;
- migration/rollback plan;
- deployment/E2E evidence.
