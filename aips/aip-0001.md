## Abstract

Defines the process by which all other AIPs are created, reviewed, and ratified. Modeled on Ethereum EIPs, Python PEPs, and the IETF RFC process.

## Motivation

Make protocol evolution transparent, reviewable, and backward-compatibility-aware.

## Specification

### AIP Types

| Type | Scope |
|---|---|
| **Standards Track** | Changes to the protocol itself (wire format, endpoints, receipts, errors, networks). |
| **Meta** | Changes to processes, governance, or the AIP process itself. |
| **Informational** | Guidelines, best practices, design notes; non-binding. |

### Proposal Lifecycle

```
Idea ──► Draft ──► Review ──► Last Call ──► Accepted ──► Final
```

### Roles

- **Author(s)** — write and champion the AIP.
- **AIP Editors** — enforce formatting, assign numbers, manage status transitions.
- **Review Board** — domain maintainers who evaluate technical merit and vote.
- **Community** — anyone may comment.

### Decision Rule

Acceptance requires rough consensus with no unresolved blocking security objection.

### Versioning

- **PATCH** — editorial/clarification; no wire change.
- **MINOR** — backward-compatible additions.
- **MAJOR** — breaking change with ≥12 months parallel support.
