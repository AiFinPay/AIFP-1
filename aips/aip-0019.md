## Abstract

Defines a dedicated error for a budget-policy breach **before an AIFP-1 payment is signed or broadcast**.

## Motivation

Agents and merchant/account policy engines need a deterministic way to refuse spending that would exceed configured limits without creating a dangerous state where the payer has already settled funds but the receipt service later denies access for budget reasons.

## Specification

### Error Code

`AIFP-403-BUDGET-EXCEEDED`

### HTTP Status

`403 Forbidden`

### Safe Trigger Point

This error is a **pre-payment policy decision**. It may be returned by a quote/policy endpoint such as `POST /v1/quote`, or exposed locally by an SDK/wallet policy check before transaction signing.

It MUST NOT be used by `POST /v1/pay` (settlement verification) to deny a receipt solely because a budget is exceeded **after** a settlement matching an already-issued payable quote has been broadcast.

Current safe lifecycle:

```text
AIFP-1 challenge
→ budget/policy check against gross payer amount
→ quote allowed or AIFP-403-BUDGET-EXCEEDED
→ local signing/broadcast only if allowed
→ /v1/pay verifies an already-executed settlement
→ receipt on successful settlement verification
```

Once the system has issued a payable quote and the payer has executed a settlement that correctly matches that quote, `/v1/pay` evaluates settlement validity, finality, replay/idempotency, and quote binding. A post-settlement budget decision MUST NOT strand valid payer funds without the corresponding receipt entitlement.

### Response Body

```json
{
  "error": {
    "code": "AIFP-403-BUDGET-EXCEEDED",
    "message": "Payment would exceed budget policy",
    "details": {
      "policy_id": "pol_*",
      "cap_type": "daily|monthly|per_request",
      "current": "<current_gross_spend>",
      "limit": "<configured_gross_limit>"
    }
  }
}
```

Monetary policy values use exact decimal/minor-unit arithmetic. For AIFP-1, budget comparisons are against the **gross payer amount**, not the 99% merchant amount.

### Trigger Conditions

Before signing/broadcasting, a policy engine may reject when the proposed gross payment would exceed:

- per-request cap;
- daily cap;
- monthly cap;
- per-merchant allowance;
- another explicitly configured payer/account spend rule.

### Idempotency And Concurrency

A durable spend cap should use atomic reservation/commit/release or an equivalent concurrency-safe mechanism so simultaneous requests cannot both pass the same remaining budget.

If a payment broadcast may already have occurred but the client is uncertain due to a transport/process failure, reconcile the existing payment/transaction identity before reserving or broadcasting again.

## Backward Compatibility

The error code is retained, but its old placement at `POST /v1/pay` is corrected because the current AIFP-1 flow submits `tx_ref` only **after** payer settlement. Implementations that still reject a correctly settled quote at `/v1/pay` solely for budget reasons are not conformant with the current protocol lifecycle.

## Security Considerations

Budget enforcement prevents runaway agent spending only when it acts before signing/broadcasting and is concurrency-safe. A post-payment budget rejection can instead create payer loss by withholding a receipt after valid funds have moved; implementations MUST avoid that failure mode.
